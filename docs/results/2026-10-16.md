## 4. 所見

- **エラーは全シナリオで 0 件。** CloudFront → OAC → Web Function → Network Connector → Valkey の経路は、50 rps の急増でも安定していた
- **サーバー内の処理は 5ms 前後**で、そのうち Valkey が 3〜5ms。クライアントから見た応答時間（med 20〜27ms）の大半は、CloudFront とオリジン（Web Function のエンドポイント）のあいだのネットワーク経路が占めている。静的ファイル（CloudFront で完結）が med 6ms なので、オリジンまでの往復とサーバー処理で 15〜20ms ほど上乗せされている計算になる
- **負荷を 10 → 50 rps に上げても、中央値と p95 はほとんど変わらなかった。** なお、当初は「この規模なら 1 つの実行環境で処理しきれている」と考えていたが、ログを見ると実際には 6 つの実行環境に振り分けられていた（6.1 節）
- **p95 は p90 から急に上がる（`GET /` で 45ms → 66ms）。** アプリ内の p95 は 6〜13ms なので（6.1 節）、この差はアプリではなくネットワーク経路（CloudFront とオリジンのあいだ）で生じている
- **max は 250〜330ms。** ログで確認したところ、すべて新しい実行環境の最初のリクエスト（Valkey への初回接続）だった（6.2 節）
- **NAT 経由の外部通信**（祝日 API）は med 38.7ms。外部 API 自体の応答時間を含むので、NAT の経由分だけを切り出した値ではない

### コールドスタート

- **何分でゼロまでスケールインするかは、今回の計測からは結論を出せない。** 計測中に外部（ボット）からのアクセスがあり、5 分と 15 分の結果は、その直前のアクセスで立ち上がっていた実行環境で処理されていた（6.3 節）
- **本当のコールドスタート（30 分と 60 分）の TTFB は 1.4〜1.6 秒。** 内訳は 6.4 節。15 分の 387ms は、すでに起動していた実行環境に当たったもので、最初のリクエストでだけ発生する処理（Secrets Manager の取得、Valkey への接続、Next.js の初回処理。6.4 節の ④ に相当）だけの遅延だった
- **アプリ側のコールドスタートの負担は約 250ms。** 内訳は、Secrets Manager の取得（NAT 経由）が 85〜104ms、Valkey への接続（TLS とクラスタ構成の取得）が数 ms〜10ms ほど、最初のコマンドが 54〜66ms（クラスタの各ノードへの接続を含む）
- **画面の初回表示も遅い。** 同じ実行環境で 2 リクエスト目の `/` でも、サーバー total が 133〜145ms かかった。ページのモジュールの初回読み込みと、Valkey のほかのノードへの初回接続によるものと考えられる
- **5 分待った後のウォーム時でも、TTFB に 100ms 前後の上乗せがあった**（サーバー total は 5ms 前後）。CloudFront とオリジンのあいだの接続を、作り直したためと考えられる

### 6.5 計装についての注意

- ヘッドルームとして、リクエストより前に立ち上がる実行環境がある。たとえば `sjmxopyh` は、起動（07:21:54）してから 5 分後（07:26:53）に最初のリクエストを受けた
- この場合、ログの `coldStart=1` でも、利用者から見た遅延は 6.4 節の ④ の分（約 250ms）だけになる。**`coldStart` は「その実行環境で最初のリクエスト」という意味で、「利用者がコールドスタートを体験した」とは限らない**
- 利用者が体験したかどうかを区別するため、計測の後に、最初のリクエストのログへ「待ち受けを始めてからの経過時間」（`sinceReadyMs`）を出すようにした。数百 ms なら起動を待っていた、数秒以上なら先に起動していた実行環境に後から届いた、と判断できる
