- 構成: 設計書のとおり（実行環境あたりの最大同時リクエスト数 64、タイムアウト 30 秒）

### サーバー内の処理時間（Server-Timing、curl で各 30 回）

| 対象 | クライアントの TTFB（med / p90） | サーバー total（med / p90） | うち Valkey（med / p90） |
| --- | --- | --- | --- |
| `GET /` | 36.9 / 50.1 | 5.3 / 6.6 | 5.5 / 6.1 |
| `GET /api/health` | 33.7 / 38.6 | 4.0 / 5.8 | 2.6 / 3.2 |

- curl は毎回新しく接続するため、TTFB には CloudFront との TLS ハンドシェイクが含まれる。k6（接続を使い回す）の値より大きい
- `GET /` の `valkey` は、並行して実行するコマンド（一覧と祝日キャッシュの取得）の合計なので、`total` を上回ることがある。また `total` はレスポンスヘッダを送った時点までの時間（ストリーミングのため）

## 4. 所見

- **エラーは全シナリオで 0 件。** CloudFront → OAC → Web Function → Network Connector → Valkey の経路は、50 rps の急増でも安定していた
- **サーバー内の処理は 5ms 前後**で、そのうち Valkey が 3〜5ms。クライアントから見た応答時間（med 20〜27ms）の大半は、CloudFront とオリジン（Web Function のエンドポイント）のあいだのネットワーク経路が占めている。静的ファイル（CloudFront で完結）が med 6ms なので、オリジンまでの往復とサーバー処理で 15〜20ms ほど上乗せされている計算になる
- **負荷を 10 → 50 rps に上げても、中央値と p95 はほとんど変わらなかった。** ただし、この規模では 1 つの実行環境（同時 64 リクエスト）で処理しきれている可能性が高く、スケールアウトの挙動は観察できていない
- **p95 は p90 から急に上がる（`GET /` で 45ms → 66ms）。** 一部のリクエストだけが遅い分布になっている。原因（実行環境の違い、Valkey の接続先ノード、CloudFront のエッジとオリジン間の接続の確立など）は、CloudWatch Logs のアクセスログと突き合わせて確認する必要がある
- **max は 250〜330ms。** 新しい実行環境の起動（コールドスタート）か、Valkey への初回接続の可能性がある。下記のクエリで、計測時間帯に `coldStart: true` のリクエストがあったかを確認する
- **NAT 経由の外部通信**（祝日 API）は med 38.7ms。外部 API 自体の応答時間を含むので、NAT の経由分だけを切り出した値ではない

## 5. 追加で確認するとよいこと

CloudWatch Logs のアクセスログを、計測した時間帯（UTC で 05:51〜06:10 ごろ）について集計する。

```bash

# コールドスタートになったリクエストと、実行環境の初期化時間
scripts/insights.sh 2026-10-16T05:45:00Z 2026-10-16T06:15:00Z coldstarts

# 遅かったリクエスト（max の外れ値の正体）
scripts/insights.sh 2026-10-16T05:45:00Z 2026-10-16T06:15:00Z slow
```
