- 計測元: 手元のマシン（東京）、k6 v0.53
- 構成: 設計書のとおり（実行環境あたりの最大同時リクエスト数 64、タイムアウト 30 秒）

## 3. コールドスタート

curl は毎回新しく接続するため、TTFB にはクライアントと CloudFront のあいだの TLS ハンドシェイク（数十 ms）が含まれる。

## 4. 所見

- **エラーは全シナリオで 0 件。** CloudFront → OAC → Web Function → Network Connector → Valkey の経路は、50 rps の急増でも安定していた
- **サーバー内の処理は 5ms 前後**で、そのうち Valkey が 3〜5ms。クライアントから見た応答時間（med 20〜27ms）の大半は、CloudFront とオリジン（Web Function のエンドポイント）のあいだのネットワーク経路が占めている。静的ファイル（CloudFront で完結）が med 6ms なので、オリジンまでの往復とサーバー処理で 15〜20ms ほど上乗せされている計算になる
- **負荷を 10 → 50 rps に上げても、中央値と p95 はほとんど変わらなかった。** ただし、この規模では 1 つの実行環境（同時 64 リクエスト）で処理しきれている可能性が高く、スケールアウトの挙動は観察できていない
- **p95 は p90 から急に上がる（`GET /` で 45ms → 66ms）。** 一部のリクエストだけが遅い分布になっている。原因（実行環境の違い、Valkey の接続先ノード、CloudFront のエッジとオリジン間の接続の確立など）は、CloudWatch Logs のアクセスログと突き合わせて確認する必要がある
- **max は 250〜330ms。** 新しい実行環境の起動（コールドスタート）か、Valkey への初回接続の可能性がある。下記のクエリで、計測時間帯に `coldStart: true` のリクエストがあったかを確認する
- **NAT 経由の外部通信**（祝日 API）は med 38.7ms。外部 API 自体の応答時間を含むので、NAT の経由分だけを切り出した値ではない

### コールドスタート

- **アクセスしない状態が 5〜15 分続くと、実行環境が入れ替わる。** 5 分の時点では同じ実行環境が残っていた（Secrets Manager の再取得がない）。15 分以降は、毎回新しい実行環境で処理された
- **コールドスタート時の TTFB は 0.4〜1.6 秒。** 15 分では 387ms だったが、30 分と 60 分では 1.4〜1.6 秒になった。サーバー total（アプリの処理）はどれも約 250ms で変わらないので、差の約 1.1 秒は、アプリより手前の実行環境の起動（Node.js と Next.js の起動を含む）にかかっている。15 分のときは、何らかの理由で起動が速く済んだと考えられるが、原因は不明（ログの `uptimeMs` で確認する）
- **アプリ側のコールドスタートの負担は約 250ms。** 内訳は、Secrets Manager の取得（NAT 経由）が 85〜104ms、Valkey への接続（TLS とクラスタ構成の取得）が数 ms〜10ms ほど、最初のコマンドが 54〜66ms（クラスタの各ノードへの接続を含む）
- **画面の初回表示も遅い。** 同じ実行環境で 2 リクエスト目の `/` でも、サーバー total が 133〜145ms かかった。ページのモジュールの初回読み込みと、Valkey のほかのノードへの初回接続によるものと考えられる
- **5 分待った後のウォーム時でも、TTFB に 100ms 前後の上乗せがあった**（サーバー total は 5ms 前後）。CloudFront とオリジンのあいだの接続を、作り直したためと考えられる

### 改善の候補（未実施）

| 候補 | 期待できる効果 | 注意点 |
| --- | --- | --- |
| 起動時に Secrets Manager の取得と Valkey への接続を済ませる（Next.js の `instrumentation.ts` の `register()` で行う） | 1 リクエスト目から約 250ms を取り除ける可能性がある（起動の時間に移る） | 起動自体は速くならない。初期化のタイムアウトに注意する |
| Secrets Manager を VPC エンドポイント経由にする | NAT 経由（85〜104ms）より速くなる可能性がある | VPC エンドポイントの固定費（1 AZ あたり月約 10 USD）がかかる |
| 定期的にアクセスして実行環境を温めておく | コールドスタートの頻度を減らせる | アクセスしない時間にも費用がかかる。15 分より短い間隔が必要 |

## 5. 追加で確認するとよいこと

CloudWatch Logs のアクセスログを、計測した時間帯（負荷試験は UTC で 05:51〜06:10 ごろ、コールドスタートは 06:10〜08:01）について集計する。

```bash
# 実行環境ごとのリクエスト数と遅延（スケールアウトしたか、遅い実行環境があるか）
scripts/insights.sh 2026-10-16T05:45:00Z 2026-10-16T06:15:00Z environments

# コールドスタートになったリクエストと、実行環境の初期化時間
scripts/insights.sh 2026-10-16T05:45:00Z 2026-10-16T06:15:00Z coldstarts

# 遅かったリクエスト（max の外れ値の正体）
scripts/insights.sh 2026-10-16T05:45:00Z 2026-10-16T06:15:00Z slow

# コールドスタートの計測時間帯の、実行環境の起動時間（uptimeMs）
scripts/insights.sh 2026-10-16T06:10:00Z 2026-10-16T08:05:00Z coldstarts
```
